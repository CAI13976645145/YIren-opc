### 2.10 SSH 扫描与对话滚动修复（0.26 补充验证）

**问题 1：SSH 扫描失败**

现象：扫描 3090 服务器报 `Warning: Identity file 13976645145 not accessible` + `Permission denied (publickey,password)`。

根因有两个：一是「SSH 私钥路径」填的是手机号，不是文件路径，代码原样传给 `ssh -i`；二是 `execFile` 的报错只显示 `Command failed: ssh ...`，把 ssh 自己输出的真实原因丢掉了。

修复：

- 私钥路径支持 `~` / 相对文件名，依次到 `data/ssh`、`~/.ssh`、当前目录解析；找不到就报「私钥文件不存在」并列出可用密钥
- 新增 `GET /api/servers/ssh-keys`，设置页私钥字段改成带下拉的输入框（本机 6 把密钥全部列出）
- `ssh-test` 支持未保存的表单直接测试，失败会返回原因、建议密钥，并自动填入输入框
- `sshExec` 捕获 stderr，把 Permission denied / 主机指纹 / 超时 / 端口拒绝翻译成中文可执行提示
- 增加 `StrictHostKeyChecking=accept-new` 与 `ServerAliveInterval=5`，首次连接不再因为指纹校验失败
- 扫描结果带进程名与常见端口名（Ollama / ComfyUI / Netdata / SSH…）
- 顺手修了远程指标内存为 0：中文 locale 下 `free` 输出「内存：」，改为 `LC_ALL=C` 并兼容匹配

验证（192.168.110.5）：

| 项 | 结果 |
| --- | --- |
| 错误提示 | 「私钥文件不存在：13976645145。看起来你想用 id_ed25519_srv3090」 |
| 正确密钥测试 | 连接成功 161–171ms，主机名 youlisi-OMEN-30L-Desktop-GT13-1xxx |
| 扫描服务 | 12 个监听端口，含 python :11434（Ollama）、python :8188（ComfyUI）、Netdata :19999、SSH :22 |
| 性能指标 | CPU 0.3% / 内存 12.1% / 磁盘 51.0% / 运行 3 天 |

**问题 2：对话总是自动回到底部**

根因：`renderChatDock()` 每次都整块重建消息列表并无条件 `scrollTop = scrollHeight`；流式每个 chunk、每 5 秒轮询都会触发一次，用户往上翻立刻被拽回。

修复：重建前记录是否停在底部（阈值 80px）与当前 `scrollTop`；不在底部就还原位置。切换会话、自己发消息才强制到底；新增「回到最新 ↓」按钮。同时移除全局 `scroll-behavior: smooth`，避免流式跟随被动画拖慢。

验证：40 条消息铺满后手动上滚到 2490px，触发 `render()` 后仍在 2490px；「回到最新」按钮出现；点击后回到底部（3223/3228），控制台 0 报错。

### 2.14 审批策略、任务超时与版本号（0.30 补充验证）

**问题 1：员工一直卡在审批，无法无人运行**

根因：

- 预审模型把请求当成任务来执行，返回自然语言，`max_tokens` 只有 200，经常内容为空 → 全部按「预审不可用，转人工」
- `deterministicWriteAllow` 只放行「10 分钟内新建的文件」，工位/项目内修改已有文件永远转人工
- 只读脚本（变量赋值 + Get-ChildItem 等）被 `classifyShellCommand` 判成 L3
- 越界的新文件会被 L1 自动放行策略误放行

- 新增风险引擎：low / medium / high / critical（红线），规则见下表
- AI 预审改为 JSON 输出 + 600 tokens + 文本关键词兜底；AI 只负责「加风险」，不可用时按确定性规则判断，不再一律卡人工
- 只读脚本识别：变量赋值 + Get-ChildItem / Select-Object / Format-Table 等查询命令 → L0 自动放行
- L1 自动放行增加风险约束：只放行 non-critical / non-high
- 新增三档审批模式：严格 / 平衡（默认）/ 全自动；设置页可切换
- 审批卡显示风险等级与判断依据
- 历史遗留的只读审批会在读取状态时自动复核放行，不再需要人工清队列

风险表：

| 风险 | 场景 | 平衡模式 |
| --- | --- | --- |
| low | 工位/项目内新建文件、只读命令 | 自动 |
| medium | 工位/项目内修改文件、补丁、常见构建/测试命令 | 自动 |
| high | 未识别终端命令、AI 判高风险 | 人工 |
| critical | 删除、密钥、越界、安装、推送、联网 | 人工（所有模式） |

| 工位内新建文件 | risk=low，autoBy=policy，自动放行 |
| 工位内修改已有文件 | risk=medium，autoBy=risk-medium，自动放行 |
| 删除命令 | risk=critical，pending（人工） |
| 越界写入 | risk=critical，pending（人工） |

## 3. 发现的问题

### 3.1 P0 · dsh 会话上限 32 导致整站不可用（已修复）

**现象**

- 回归跑到第二轮时，`POST /api/chat/stream` 返回 `session limit reached (32)`，`POST /api/chat` 返回 502 `DSH_UNAVAILABLE`
- `GET /opc-runtime/v1/health` 显示 `sessionCount: 32`，此后任何新会话都创建失败
- 任务页出现连续「自动执行任务失败：session limit reached (32)」

**根因**

- `opc-runtime-bridge` 的 `MAX_SESSIONS = 32`，只增不删，也没有 DELETE 接口
- 本产品按场景建会话：`员工`、`员工:项目`、`员工:任务`、`员工:会议`
- 任务维度会话是**每任务一条**，10 员工 × 多任务很快超过 32 → 聊天、任务、会议全部不可用

**修复**

1. `opc-runtime-bridge` 升级到 `0.2.3-session-evict`
   - 上限 32 → **64**（可用 `OPC_BRIDGE_MAX_SESSIONS` 覆盖）
   - 达到上限前**自动淘汰最久未用的空闲会话**（`prompting` 中的不淘汰）
   - 新增 `GET /sessions`（列表）、`DELETE /sessions/:id`（显式关闭，忙时 409）
   - 记录 `lastUsedAt` 用于 LRU
2. `lib/dsh-bridge.mjs`
   - 遇到 `SESSION_LIMIT/429` 时自动回收 8 个空闲会话并**重试一次**
   - 新增 `listBridgeSessions` / `closeSession` / `reclaimIdleSessions`
   - 本地会话表超过 **120** 条时淘汰最久未用并通知 bridge 释放

**验证**

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 连续创建 75 个会话 | 第 33 个开始 429 | **75 个全部成功**（0 失败） |
| 会话总数 | 32（卡死） | 稳定在 64 上限内（LRU 回收 11 个） |
| 显式关闭 | 无接口 | `DELETE` 返回 200，63 个会话一次清空 |
| 聊天 / 群聊 / 任务 | 全部 502/429 | 回归 4/4 通过 |

> 修复后完整回归再跑：**126/126 全绿**。
